# DocuBot AI — Claude Code Project Instructions

## 1. Project Identity

Project name: DocuBot AI

Project purpose:

Build a production-oriented RAG Telegram knowledge assistant.

Core product:

User uploads documents through a web interface.
The system processes the documents into a searchable knowledge base.
The user asks questions through Telegram.
The system retrieves relevant document evidence and generates an answer with citations.

Target architecture will evolve gradually:

Web Upload
→ Document Processing
→ Chunking
→ Embedding
→ Vector Search
→ RAG
→ Telegram
→ Advanced Retrieval
→ Agent
→ Evaluation
→ Observability
→ Security
→ Production Deployment.

Do NOT build the entire final architecture at the beginning.

---

## 2. Developer Profile

The project owner is a complete beginner learning AI Engineering from zero.

Do not assume advanced knowledge of:

* Computer Science
* Python
* Git
* Backend Engineering
* HTTP / REST
* SQL
* Databases
* Embeddings
* Vector Search
* RAG
* AI Agents
* DevOps
* Cloud

The goal is not only to make the software work.

The developer must understand:

What it is
Why it exists
How it works
When to use it
When not to use it
What can go wrong
How to test it
How it fits into production AI systems

---

## 3. Teaching Mode

Use Simplified Chinese for explanations.

Keep important English technical terms.

When introducing an important technical term for the first time, explain it using:

English term
→ simple Chinese explanation
→ practical example

After each implementation, explain:

1. What changed
2. Which files changed
3. Why the change was necessary
4. How the code works
5. How the runtime flow works
6. Important technical concepts
7. Common beginner mistakes
8. How to test it
9. Actual test result
10. What this teaches for Production AI Engineering

Do not assume the developer already understands code generated by AI.

---

## 4. Development Workflow

For every task, follow this order:

Inspect
→ Understand
→ Plan
→ Implement
→ Test
→ Review
→ Explain
→ Commit when appropriate

Before modifying code:

1. Inspect the relevant files.
2. Understand existing architecture.
3. Check existing dependencies.
4. Check existing tests.
5. Identify the smallest necessary change.

Do not immediately start coding without inspecting the existing project.

---

## 5. Scope Control

Work only on the current milestone.

Do not implement future features unless explicitly requested.

For example:

If the current milestone is Telegram Hello World:

Do NOT add:

* RAG
* PostgreSQL
* pgvector
* Embeddings
* Agents
* Redis
* Kubernetes
* Cloud infrastructure

Keep the implementation minimal.

Future architecture may be documented, but future functionality should not be implemented prematurely.

---

## 6. Safe Code Changes

Do not rewrite unrelated code.

Do not delete working logic unless there is a clear reason.

Do not rename files or APIs unnecessarily.

Do not introduce unnecessary dependencies.

Prefer the smallest maintainable change.

Before changing important existing logic, explain the reason.

Never hide errors simply to make tests pass.

Never weaken or delete tests just because they fail.

---

## 7. Testing Requirements

Every meaningful implementation must be verified.

Use appropriate:

* Unit tests
* Integration tests
* Manual tests
* API tests
* End-to-end tests

Do not claim that something works unless it has actually been tested.

When a test fails:

1. Show the failure.
2. Identify the likely root cause.
3. Investigate.
4. Fix the actual problem.
5. Re-run the test.
6. Report the final result.

Tests are part of the project and must be preserved.

---

## 8. Secrets and Security

Never hardcode:

* Telegram Bot Token
* LLM API Key
* Database Password
* JWT Secret
* OAuth Secret
* Other credentials

Use environment variables.

Never expose secrets in source code, logs, README files, screenshots, tests, or Git history.

`.env` must not be committed to Git.

Be especially careful because this repository is intended to become a public GitHub portfolio.

---

## 9. Git Rules

Before significant changes:

Check the current Git state.

Do not discard user changes.

Do not force reset the repository unless explicitly requested.

Prefer small logical commits.

Commit messages should describe the actual change.

Git history should gradually demonstrate project evolution.

---

## 10. Architecture Principles

Prefer simple architecture first.

Avoid premature abstraction.

Avoid unnecessary microservices.

Avoid unnecessary frameworks.

Prefer clear boundaries between:

* API
* Document Processing
* Retrieval
* LLM
* Telegram
* Database
* Evaluation
* Observability

The architecture should become more advanced only when the relevant project milestone requires it.

---

## 11. RAG Principles

When implementing RAG, keep these concepts separate:

Document Ingestion
Chunking
Embedding
Indexing
Retrieval
Reranking
Context Assembly
Generation
Citation
Evaluation

Do not describe the entire system as “RAG” without explaining which stage is responsible for a problem.

When an answer is wrong, distinguish between:

* Retrieval failure
* Context construction failure
* Generation failure
* Application logic failure

---

## 12. Beginner-Friendly Coding

Prefer:

* readable code
* clear names
* small functions
* simple control flow
* useful comments
* type hints where appropriate
* explicit error handling

Avoid:

* giant functions
* unnecessary abstraction
* obscure shortcuts
* unnecessary design patterns
* premature optimization
* unnecessary frameworks

Generated code should remain understandable to a beginner.

---

## 13. AI-Assisted Development Rules

Claude Code is an engineering assistant, not the owner of the architecture.

The developer must remain informed about major decisions.

For significant architectural changes:

Explain:

* Problem
* Proposed solution
* Alternatives
* Trade-offs
* Why the chosen approach fits the current milestone

Do not silently make major architecture decisions.

Do not generate large amounts of code when a smaller implementation is sufficient.

## 16. Verification Standard

Before reporting a completed task, verify:

1. Files are in the expected locations.
2. Code is syntactically valid.
3. Relevant tests pass.
4. The implementation behaves as intended.
5. No unrelated functionality was changed.
6. No secrets were exposed.
7. Git diff matches the requested task.

If something cannot be verified, explicitly say so.

---

## 17. Current Project Rule

At the beginning of every new task:

First inspect the repository and current Git state.

Then determine:

* What already exists
* What the current milestone is
* What must change
* What must NOT change

Do not continue to the next milestone automatically.

Wait for the developer to request the next milestone.
